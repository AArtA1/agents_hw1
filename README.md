# Repo Agent — ассистент по публичному репозиторию

**Выполнили:** Асланян Артак, Блинов Савва

Индексирует репозиторий (код, README, история коммитов, issues), отвечает на вопросы со ссылками
`файл:строки`, строит автосводку проекта и карту модулей, делает простое ревью (баги и
проблемы безопасности) и считает метрики качества.

| Что требуется | Где реализовано |
|---|---|
| Индекс кода, README, истории коммитов (+ issues) | `repo_agent/index.py`, `chunking.py`, `repo.py`, `issues.py` |
| Чат с привязкой к файлам и строкам | `repo_agent/agent.py` (цикл), `tools.py` (11 инструментов: схемы, валидация, таймауты), `citations.py` (проверка ссылок) |
| Автосводка: стек, точки входа | `repo_agent/summary.py` |
| Схема модулей | `repo_agent/modmap.py` (граф импортов Python / JS / TS / Go → Mermaid) |
| Отчёт ревью: баги и безопасность | `repo_agent/review/` (статические правила + LLM-ревью файлов или коммита с issues) |
| Метрика «доля ответов с верным файлом» | `repo_agent/eval/qa.py`, `eval/datasets.py` (SWE-QA, StackRepoQA, CodeRepoQA, свой JSONL) |
| Метрика «доля найденных внесённых багов» | `repo_agent/eval/bugs.py` (мутации + реальные баги из fix-коммитов, с контролем) |
| Интерфейс | `app.py` (Streamlit), `repo_agent/cli.py` (CLI), HTML-отчёт `repo_agent/report.py` |

## Спецификация агента (ДЗ 1 «Агент с инструментами»)

**Пользователь** — разработчик, который впервые открывает чужой публичный репозиторий (новичок в
команде, ревьюер PR, автор issue). **Его задачи:** быстро понять, где что лежит и как работает
(«где задаётся число повторов у HTTPAdapter?»), получить ответ со ссылками `файл:строки`, которые
можно проверить, узнать историю изменения кода и найти потенциальные баги и уязвимости.

**Опасные действия.** Все инструменты, кроме одного, только читают локальный клон и индекс.
Единственное действие с побочным эффектом — `create_issue` (оформить issue о найденной проблеме):
оно пишет файл, а при `actions.post_to_github = true` и заданном `GITHUB_TOKEN` публикует issue в
чужом репозитории от имени пользователя. Поэтому оно **никогда не выполняется без подтверждения
человеком**: в CLI агент останавливается и спрашивает `Выполнить? [y/N]`, в веб-интерфейсе действие
появляется с кнопками «Подтвердить / Отклонить», а модель получает «ожидает подтверждения». Другие
риски: содержимое репозитория и issues — недоверенные данные (промпт говорит не выполнять найденные
там инструкции), путь вне индекса прочитать нельзя.

**Сценарии ошибок и что делает агент**

| Сценарий | Что видит модель | Что делает агент |
|---|---|---|
| Модель передала аргументы не по схеме (`start_line: "10"`, лишнее поле) | `Ошибка аргументов read_file: поле 'start_line' должно быть integer …` (`is_error`) | исправляет аргументы и повторяет |
| Файла нет / путь неточный | `Ошибка: файл '…' не найден в индексе. Найди путь через search_code…` | ищет путь через `search_code`/`list_dir` |
| Таймаут сервиса (git, GitHub API, долгий grep) | `Таймаут: … повтори вызов один раз … или продолжи без этого инструмента` | повторяет один раз или обходится без инструмента и говорит, что не проверено |
| Модель (Claude API) недоступна / таймаут | — | агент не падает: возвращает «⚠️ Модель недоступна», история диалога остаётся корректной |
| Ответ модели оборвался посреди вызова инструмента | `Не выполнено: ответ модели был обрезан` | история не ломается, следующий вопрос работает |
| Слишком большой результат | результат обрезан до `max_tool_output_chars` с пометкой | сужает запрос |
| Исчерпан лимит шагов | на последнем шаге инструменты отключены | отвечает по уже собранным данным |
| Человек отклонил действие | `Человек ОТКЛОНИЛ действие; оно НЕ выполнено` | сообщает пользователю, не повторяет |

### Карточки инструментов (8 полей)

Всего у агента 11 инструментов (10 только читают, 1 действие); схемы — в
[`repo_agent/tools.py`](repo_agent/tools.py). Ниже — подробно три ключевых.

| Поле | `search_code` | `read_file` | `create_issue` |
|---|---|---|---|
| **Имя** | `search_code` | `read_file` | `create_issue` |
| **Описание** (то, что видит модель) | Найти, где в репозитории код/документация по теме; использовать первым, когда неизвестен файл; запрос — 2–6 ключевых слов или идентификаторов; результат — не полный код, затем читать через `read_file` | Прочитать строки файла с номерами (≤ 250 за вызов), чтобы проверить код и получить точные номера строк для ссылок; подсказка, откуда читать дальше | ДЕЙСТВИЕ: подготовить issue о найденной проблеме; вызывать только по прямой просьбе; выполняется только после подтверждения человеком; не утверждать, что issue создан, пока это не подтвердил результат |
| **Аргументы** (схема, `additionalProperties: false`) | `query`: string 2–300 (обяз.); `path_prefix`: string ≤ 300; `k`: integer 1–20 | `path`: string 1–400 (обяз.); `start_line`, `end_line`: integer ≥ 1 | `title`: string 5–120 (обяз.); `body`: string 20–8000 (обяз.); `labels`: array of string, ≤ 5 |
| **Что не от модели** | какой репозиторий и его индекс — из сессии (`RepoIndex`) | корень клона на диске и список разрешённых файлов — из сессии; путь вне индекса не читается | owner/name репозитория — из сессии; `GITHUB_TOKEN` — из окружения; разрешение публиковать — из конфига (`actions.post_to_github`); решение — от человека |
| **Результат** | до `k` фрагментов: `путь:начало-конец (score) symbols: …` + 8 строк превью; обрезка до `max_tool_output_chars` | `путь (строки a-b из N)` + строки `   номер \| текст`; длинные строки обрезаются до `max_line_chars` | `Черновик issue сохранён: <путь>` или `Issue создан на GitHub: <url>`; до подтверждения — `ОЖИДАЕТ ПОДТВЕРЖДЕНИЯ ЧЕЛОВЕКОМ` |
| **Ошибки** | ошибка аргументов; пустой результат («Ничего не найдено. Попробуй…») | ошибка аргументов; файл не найден; `start_line` за концом файла; `end_line < start_line`; таймаут (симулируемый в демо) | ошибка аргументов; ошибка/таймаут GitHub API (черновик всё равно сохраняется локально) |
| **Тип** | чтение (локальный индекс), без побочных эффектов | чтение (файлы клона), без побочных эффектов | **действие** с побочным эффектом (запись файла / публикация на GitHub) |
| **Отказ** | при ошибке модель меняет запрос или переходит к `find_symbol`/`grep`; повтор одного и того же неудачного вызова — не больше двух раз | при «не найден» — ищет путь; при таймауте — повтор один раз, иначе отвечает с оговоркой, что не проверено | человек нажал «Отклонить» / ответил не `y` / нет терминала → действие не выполняется, модель получает «ОТКЛОНИЛ» и сообщает пользователю |

Остальные инструменты: `find_symbol`, `grep` (ограничен по времени), `list_dir`, `git_history`,
`show_commit`, `blame` (git с таймаутом), `search_issues`, `get_issue` (GitHub API с таймаутом).

### Демо (3 минуты)

```bash
export ANTHROPIC_API_KEY=...
uv run repo-agent index psf/requests
# 1) обычный сценарий и 2) сценарий, где read_file вернул таймаут, а агент повторил вызов и ответил:
uv run repo-agent demo psf/requests
# любой вопрос со сбоем выбранного инструмента:
uv run repo-agent ask psf/requests "Как Session объединяет настройки?" --fault read_file:timeout
# действие с подтверждением человеком:
uv run repo-agent ask psf/requests "Найди слабое место в обработке no_proxy и оформи issue"
# если на паре нет сети/ключа — тот же цикл с записанными решениями модели
# (видны ошибка аргументов → исправление и таймаут → повтор):
uv run repo-agent demo psf/requests --offline
```

В веб-интерфейсе (`uv run streamlit run app.py`): в боковой панели «Демо: симулировать сбой
инструмента» → задать вопрос → в «Шагах агента» видно ⏱️ timeout и следующий успешный вызов;
предложенное агентом действие появляется с кнопками «Подтвердить / Отклонить».

## Установка

```bash
uv sync                                  # Python 3.12, зависимости: anthropic, streamlit
export ANTHROPIC_API_KEY=sk-ant-...      # без ключа всё работает, кроме LLM-частей
export GITHUB_TOKEN=...                  # необязательно: повышает лимит GitHub API для issues
```

## Быстрый старт

```bash
uv run repo-agent index psf/requests                  # клон + индекс + последние 200 issues
uv run repo-agent summary psf/requests                # стек, точки входа, структура, история
uv run repo-agent map psf/requests                    # карта модулей в Mermaid
uv run repo-agent ask psf/requests "Как Session объединяет настройки запроса и сессии?"
uv run repo-agent chat psf/requests                   # интерактивный чат
uv run repo-agent review psf/requests                 # ревью самых рискованных файлов
uv run repo-agent review psf/requests --commit <sha>  # ревью коммита (+ issues из «#123» в сообщении)
uv run repo-agent report psf/requests                 # workspace/psf__requests/report.html

uv run streamlit run app.py                           # веб-интерфейс
```

Репозиторий задаётся как `owner/name`, URL GitHub или локальный путь. Данные лежат в
`workspace/<owner>__<name>/` (клон, индекс в JSON, отчёты, результаты оценок).

## Как это устроено

**Индекс.** `git ls-files -z` (не-ASCII имена сохраняются) → фильтр: без vendor/node_modules,
бинарников, lock-файлов и переводов документации (`docs/<язык>/…`) → фрагменты. Фрагменты
начинаются с определений: для Python — точные AST-диапазоны функций/классов (с декораторами,
включая определения внутри `if`/`try`), для остальных языков — от одного определения до
следующего. Символы извлекаются через AST для Python и регулярными выражениями для JS/TS
(функции, стрелочные функции с типами, `obj.method = function`, методы классов), Go, Rust,
Java/Kotlin, Ruby, PHP. Поиск — BM25 с токенизацией по идентификаторам (`getEnvironProxies` →
`get`, `environ`, `proxies`), путь и символы весят ×3, тесты/документация слегка понижаются.
Нумерация строк везде совпадает с git/GitHub (разделитель — только `\n`). Отдельные BM25-индексы
по коммитам (до 300) и issues/PR (до 200, через GitHub API).

**Чат-агент.** Claude (модель из `repo_agent.toml`) в цикле вызывает инструменты: `search_code`,
`read_file`, `find_symbol`, `grep`, `list_dir`, `git_history` (с `--follow`), `show_commit`,
`blame` (автор и дата), `search_issues`, `get_issue`. Системный промпт требует прочитать код
перед утверждением и ставить ссылки `path:START-END`. Каждая ссылка проверяется по индексу
(файл существует, строки в пределах файла; URL не принимаются за ссылки) — в UI это ✓/✗,
просмотр кода с отмеченными строками и ссылка на GitHub на нужный коммит. Не больше 12 шагов;
если ответ модели оборвался посреди вызова инструмента, история остаётся корректной; длинный
диалог сворачивается в краткое резюме. Без ключа API чат работает в режиме поиска.

**Сводка.** Детерминированно: языки по строкам; зависимости делятся на рабочие (фреймворки) и
инструменты разработки; точки входа по приоритету — console scripts, `npm bin`, `python -m`
(с учётом src-раскладки), `func main`, публичный API библиотеки (`__init__.py` пакета),
`main`/`exports`/неявный `index.js` в `package.json`, Flask/FastAPI-приложения (только реальный
код, не примеры в докстрингах), Docker/Procfile, `__main__`-скрипты. Точки входа в docs/examples
считаются отдельно и не вытесняют основные. По флагу `--llm` Claude пишет краткое описание.

**Карта модулей.** Граф внутренних импортов: Python (AST; относительные импорты разрешаются в
подмодуль или пакет; импорты под `if TYPE_CHECKING:` не считаются), JS/TS (`import`/`require`;
`./x.js` сопоставляется с `x.ts`; алиасы `paths`/`baseUrl` из tsconfig; `require('../..')` —
корень пакета), Go (узлы — пакеты), Java/Kotlin (`import` и классы того же пакета), Rust
(`mod`, `crate::`/`super::`, межкрейтовые `use` в workspace).
Документация и примеры по умолчанию исключены. Если файлов немного — показываются файлы по
каталогам, иначе граф сворачивается до каталогов; выводятся хабы и взаимные импорты.

**Ревью.**
1. *Статические правила*: голый `except` (кроме `except: …; raise`), проглатывание исключений,
   изменяемые аргументы по умолчанию, `is` с литералом, сравнение с самим собой, дубли ключей,
   `eval`/`exec`/`os.system`/`pickle`, `subprocess(shell=True)`, `yaml.load` без Loader,
   `verify=False`, MD5/SHA1, SQL через форматирование строк, секреты (AWS, GitHub, приватные
   ключи, пароли; заглушки вроде `apiKey = "apiKey"` или `changeme` отбрасываются), XSS и
   `child_process.exec` в JS, `Runtime.exec`/десериализация/MD5 в Java, отключённый TLS и
   shell-команды в Rust. Правила не срабатывают внутри строк и комментариев, учитывают
   `# noqa` / `# nosec`; в тестах, docs и examples замечания понижаются до `low`.
2. *LLM-ревью*: Claude получает самые рискованные файлы или diff коммита с номерами строк
   (+ связанные issues) и возвращает замечания по JSON-схеме (structured outputs).

## Метрики

### Доля ответов с верным файлом (`eval-qa`)

**Главная метрика — `primary_hit`: первый файл, на который сослался ответ, эталонный.** Её нельзя
«накрутить», перечислив много файлов. Дополнительно: `file_hit@3` (эталонный файл среди первых
трёх), валидность ссылок, BM25 hit@k, LLM-судья (`--judge`) и 95% доверительные интервалы.
Для честного сравнения считается **baseline «популярный файл»**: всегда называть самый частый
эталонный файл датасета, не читая вопрос.

Датасеты:
* **SWE-QA** (`--dataset swe-qa`, 15 Python-репозиториев). Эталон — файлы кода (включая тесты,
  если ответ называет их путём), упомянутые в эталонном ответе. Неоднозначное имя (`app.py`)
  разрешается по каталогам других упомянутых путей, а если подсказки нет — эталоном считаются все
  его рабочие (не тестовые) варианты. docs/CHANGES/конфиги эталоном не считаются; голое имя,
  указывающее только на тест («файл wsgi.py»), — упоминание соглашения, а не эталон.
* **StackRepoQA** (`--dataset stackrepoqa`, вопросы Stack Overflow по 134 Java-репозиториям,
  ≤ 10 вопросов на репозиторий). Эталонных файлов в данных нет; эталон — файлы репозитория,
  названные по классам из кода принятого ответа. **Это слабая разметка**: это API-классы, которыми
  пользуется ответ, а не обязательно файл, отвечающий на вопрос; один класс часто доминирует
  (на jcommander `JCommander.java` — эталон во всех 7 вопросах, baseline «популярный файл» = 100%),
  а имя класса часто встречается в самом вопросе. Числа на StackRepoQA — только ориентир.

Для каждого вопроса отмечается **утечка** — имя эталонного файла написано в самом вопросе; метрика
отдельно считается на вопросах без утечки (`primary_hit_no_leak`).
* **CodeRepoQA** (`--dataset coderepoqa:<файл>`): распространяется через Google Drive, поэтому
  загружается из локального JSON/JSONL с issue-объектами GitHub; ответ — реплики мейнтейнеров.
* Свой JSONL: `{"question": ..., "answer": ..., "gold_files": [...]}`.

```bash
uv run repo-agent eval-qa psf/requests --mode retrieval          # baseline, без LLM
uv run repo-agent eval-qa psf/requests --mode agent --limit 20   # агент с Claude
uv run repo-agent eval-qa pallets/flask --mode agent --judge
uv run repo-agent eval-qa cbeust/jcommander --dataset stackrepoqa --mode agent
```

### Доля найденных внесённых багов (`eval-bugs`)

* **synthetic** — одна мутация на функцию: инверсии сравнений и условий, `and`↔`or`,
  off-by-one, `is None`↔`is not None`, `return True`↔`False`, а также уязвимости (`verify=False`,
  `json.loads`→`eval`, `sha256`→`md5`, `yaml.load`, `shell=True`, удаление `basename`). Мутация
  обязана изменить AST и не трогает строки, комментарии и `assert`.
* **history** — реальные баги: код до небольших содержательных fix-коммитов (коммиты про линтер,
  типы, доки, тесты, предупреждения и правки на уровне модуля отсеиваются; строки бага — только
  изменённые строки кода, не докстринги).

Ревьюер видит функцию целиком с номерами строк, без подсказки, где баг. **Найден** — есть
замечание bug/security в пределах ±2 строк от бага; замечание шире 3 строк засчитывается только по
первой строке. **Контроль** — та же функция без бага (исходный код или исправленная версия той же
функции, найденная по имени): замечание на том же месте — ложная тревога. В отчёте:
* доля найденных и доля ложных тревог (95% интервалы Уилсона);
* **различающая способность = найдено − ложные тревоги** (бутстрэп-интервал); ревьюер
  «помечаю всё» получает 0;
* точность замечаний (какая доля замечаний указывает на баг);
* случайное угадывание при том же числе замечаний, что сделал ревьюер (`chance_same_volume`);
* **«детектор артефактов мутаций»** — ревьюер, который не понимает код, а помечает строки с
  `<=`, `!=`, `is None`, `[1]`, `md5`, `eval(` и т.п. Его различающая способность показывает,
  сколько можно набрать на синтетике, просто узнавая следы мутаций; настоящий ревьюер должен
  быть заметно выше. На реальных багах из истории этот детектор даёт ≈0 — поэтому главной
  проверкой LLM-ревью считаются пробы из истории;
* разбивка по типу (bug / security). Security-мутации частично совпадают со статическими
  правилами (`md5`, `eval`, `verify=False`), поэтому их находки статикой — не показатель качества;
* `--seeds 13,1,2,3,4` — несколько выборок мутаций, среднее и разброс.

```bash
uv run repo-agent eval-bugs psf/requests --n 30 --no-llm --seeds 13,1,2,3,4   # baseline, 5 выборок
uv run repo-agent eval-bugs psf/requests --n 30                   # LLM-ревью
uv run repo-agent eval-bugs psf/requests --source history --n 30  # реальные баги (нужен полный клон)
```

## Настройки

Провайдер, модель и лимиты — в [`repo_agent.toml`](repo_agent.toml) (`[llm]`, `[agent]`, `[actions]`,
`[demo]`); любое значение переопределяется переменной `REPO_AGENT_<СЕКЦИЯ>_<КЛЮЧ>`
(например `REPO_AGENT_LLM_MODEL=claude-sonnet-5-5`). Ключи в конфиге не хранятся:

| Переменная окружения | |
|---|---|
| `ANTHROPIC_API_KEY` | ключ Claude API |
| `GITHUB_TOKEN` | токен GitHub: лимит API для issues, публикация issue (только при `actions.post_to_github = true`) |
| `REPO_AGENT_WORKSPACE` | где хранить клоны и индексы (по умолчанию `./workspace`) |
| `REPO_AGENT_CONFIG` | путь к другому TOML-конфигу |

Запросы к Claude используют prompt caching (системный промпт со сводкой и список инструментов
кэшируются между шагами агента) и серверный fallback на случай отказа классификатора безопасности
(`llm.fallbacks`).

## Ограничения

* Поиск лексический (BM25); вопросы, сформулированные совсем не словами кода (Stack Overflow),
  без агента находятся плохо. Следующий шаг — эмбеддинги и гибридный поиск.
* Карта модулей — для Python, JS/TS, Go, Java/Kotlin и Rust; динамические импорты и
  рефлексия не видны; для Java классы одного пакета связываются по упоминанию имени.
* Статические правила — эвристики, не замена Bandit/Semgrep.
* Эталон в SWE-QA и StackRepoQA извлекается из текста эталонного ответа, поэтому метрика
  «верный файл» — приближение; правильность самого ответа проверяет `--judge`.
* Внесение багов поддерживается только для Python-кода.
